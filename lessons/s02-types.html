Types

In JavaScript every number is the same kind of thing. In Java every value lives in a box of a fixed size, and you pick the box. Today: what the boxes are, what happens when a number outgrows its box, and why == on Strings seems to work right up until it doesn't.

Part 1

The type shelf

These eight are Java's primitives: raw values with no methods, that can never be null. Each one has a fixed number of bits, and the bits decide how big a number fits. You'll use the two highlighted rows for 90% of this course.

TypeSizeHoldsJS cousinObject version

Every primitive has an object version (a "wrapper") in the last column. Integer is an object that holds one int. Collections like HashMap can only store objects, which is why Two Sum used Map<Integer, Integer>. Java converts between the two for you, quietly. That quiet conversion is called autoboxing, and it's behind one of today's traps.

JS has exactly one number type, a 64-bit double. That's why 0.1 + 0.2 is off in both languages, and why JS never overflows the way Java does.

Part 4

What == actually compares

A primitive variable holds the value itself. An object variable (String, Integer, any class) holds an arrow pointing at an object somewhere else in memory. == compares what's in the variable. For objects, that means it asks "do both arrows point at the same object?" and never looks at the text. .equals() walks the arrows and compares what's inside.

The rule: use == for primitives (int, char, boolean…). Use .equals() for everything else. String literals and small Integers happen to share objects, so == often passes in quick experiments and fails later on real data. That's the betrayal. s03 draws the full memory picture.

Errors you'll probably meet today

error: incompatible types: possible lossy conversion from long to int

You're putting a long into an int box. Java refuses because the value might not fit. If you've made sure it fits (like an average of two ints), say so with a cast: (int) someLong. A cast is you promising the compiler "I checked".

error: integer number too large

A plain number in your code is an int, so 2432902008176640000 doesn't fit. Add an L to make it a long: 2432902008176640000L. Underscores are allowed for readability: 2_432_902_008_176_640_000L.

error: incompatible types: String cannot be converted to char

Double quotes make a String, single quotes make a char. 'a' is one character. "a" is a String that happens to be one character long. In JS they're the same; in Java they're different types.

error: bad operand types for binary operator '=='

Usually s.charAt(i) == "a": a char on the left, a String on the right. Java won't compare different types. Use single quotes: s.charAt(i) == 'a'.

test failure: expected: <2> but was: <0>

Not a compiler error, a logic one. In countMatches this almost always means you compared Strings with ==. The test builds its Strings at runtime, so the arrows point at different objects. Switch to .equals().
